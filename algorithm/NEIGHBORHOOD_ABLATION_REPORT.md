# 问题特定邻域与 240 秒消融报告

## 摘要

本报告始终按题目规定的顺序评价方案：先比较**逾期任务数**，相同后比较**总逾期分钟**，仍相同再比较**总里程**。

- **本次 A2 的三项均值都优于同批 A0。** A2 的三个种子均值为 `70.000` 个逾期任务、`2321.448` 分钟总逾期和 `643.948 km` 总里程；A0 分别为 `70.333`、`2338.919` 和 `647.610 km`。逐种子比较为 A2 赢 2 次、输 1 次，因此只能说均值略有改善，不能说每次都更好。
- **VND、cluster repair 和 route pool 在 240 秒内没有带来更好的三项目标。** 从 A3 开始，每秒迭代数明显下降，A3–A6 的平均逾期任务数也都高于 A2，所以这些功能不默认启用。
- **三次正式实验中得分最好的合规方案仍来自第二次报告的 ALNS Core。** 其得分为 `(67, 2161.865122 分钟, 631.416943 km)`；本次最好方案是 A0 的 `(67, 2172.800486 分钟, 631.018272 km)`。两者逾期任务数相同，但本次方案的总逾期多 `10.935` 分钟，所以即使总里程少 `0.399 km`，仍然更差。

代码默认把 A2 用于 ALNS Core：用 `assignment_destroy` 替换 `route_clear`，启用 deadline risk，并关闭 VND、cluster repair、ejection 和 route pool。HALNS 在此基础上保留 ejection search，route pool 默认关闭。本次关于 A2 默认开关的结论只来自一个 200 任务实例和三个固定种子，不作跨实例的普遍改进声明。

## 实现内容

### Assignment destroy

`assignment_destroy` 按任务的逾期贡献、deadline risk、路线绕行贡献与路线利用率选择完整取送任务对。对于 200 个任务恰好填满 8 架、每架上限 25 个任务的实例，算子在可行时至少同时从两条路线移除任务，给 repair 留出真正跨无人机重新分配的空位。

### Deadline-risk guidance

搜索引导使用单调风险指标 `delivery_time / deadline`，并对零截止期显式处理。它只影响 destroy 排名、repair shortlist/排序与局部邻域候选顺序；候选接受、当前解和最终最优解仍严格使用原三层 `Score`。

### 轻量 VND

VND 包含三类容量二、取送约束感知邻域：跨无人机 task-pair relocate、跨无人机 task-pair swap，以及短 `pickup pickup delivery delivery` block 的可行重排。所有接受动作都要求严格词典序改善；比较器还拒绝浮点聚合产生的 `1e-9` 以内“伪改善”。满载舰队中单 pair relocate 数学上没有目标空位，因此实现会快速跳过 N1，而 N2 仍可改变任务分配。

### Cluster regret repair

`cluster_regret_repair` 按取件点距离、截止期接近度和原无人机归属形成二任务 bundle，并在同一路线上联合插入。首任务位置使用小型 beam，避免只保留单任务最优位置而丢掉组合最优结构；无法形成 bundle 时回退到 regret-2。

### 墙钟与路线池

deadline 已贯穿普通 repair、cluster repair、VND 和 ejection。若某轮在墙钟边界只形成部分解，该轮会安全放弃；若 VND/ejection 已形成完整改进解，则先吸收改进再结束。route pool 没有扩张，并改为默认关闭。

## 实验设计

输入为 200 任务官方 CSV（SHA-256 `386d3fbaa9009aeed947493782d657ed0b30b25d369c8187bfc9619fc7e31d25`）。所有变体共享同一 deterministic regret-2 初始解（路线 SHA-256 `0aa05645d9ca61227c51c1d69993de896ecca045136165dec06a4bd1636288b6`），使用旧实验的三个墙钟种子 `2026080500` 至 `2026080502`。每次总预算为 240 秒：初始构造计入预算，并预留 2 秒安全余量；各变体在同一种子内轮换运行顺序。

消融按功能阶梯展开。为保持 destroy pool 大小不变、避免继续堆叠 generic operators，A1 是用 `assignment_destroy` **替换** `route_clear`，不是在 A0 上保留两者的纯加法；A2–A6 再从这个替换后的算子集逐项累加。因此 A0→A1 衡量的是替换的净效果，不能单独归因于新增算子。

| 代码 | 配置 |
|---|---|
| A0 | 改动前的 ALNS Core 算子集；新 feature flags 均关闭，含 route-clear |
| A1 | A0 - route-clear + assignment destroy |
| A2 | A1 + deadline risk |
| A3 | A2 + VND |
| A4 | A3 + cluster repair |
| A5 | A4 + ejection |
| A6 | A5 + route pool |

下表为三个种子的均值。三层目标必须按顺序解读，不能用列间加权平均替代词典序比较。

| 变体 | 逾期任务数 | 总逾期分钟 | 总里程 / km | 迭代数 | 搜索迭代/s |
|---|---:|---:|---:|---:|---:|
| A0 | 70.333 | 2338.919 | 647.610 | 1680.3 | 7.183 |
| A1 | 70.000 | 2337.179 | 649.241 | 1691.0 | 7.229 |
| A2 | 70.000 | 2321.448 | 643.948 | 1659.3 | 7.094 |
| A3 | 71.667 | 2415.850 | 648.016 | 1259.7 | 5.385 |
| A4 | 74.000 | 2481.961 | 649.880 | 1083.7 | 4.633 |
| A5 | 71.000 | 2381.170 | 666.290 | 1013.0 | 4.331 |
| A6 | 75.000 | 2675.735 | 683.648 | 723.3 | 3.092 |

21 次正式运行中，得分最好的是 A0、seed `2026080502` 的 `(67, 2172.800 分钟, 631.018 km)`；这里只记录该次结果，不据此判断某个组件是否有效。完整路线见 [`equal_wall_clock_240s__a0__seed_2026080502.json`](results/neighborhood_ablation/run_solutions/equal_wall_clock_240s__a0__seed_2026080502.json)，各变体的最好种子见 [`ablation_summary.csv`](results/neighborhood_ablation/ablation_summary.csv)。

完整的相邻配对结果为：A0 对 A1 为 2:1，A1 对 A2 为 2:1，A2 对 A3 为 3:0，A3 对 A4 为 3:0，A5 对 A4 为 2:1，A5 对 A6 为 3:0；另外 A0 对 A4 为 2:1。组合配置 A2 相对 A0 为 2:1，但 assignment replacement 和 risk 两个直接边际步骤各自只有 1 胜 2 负，所以不能把组合差异归因到任一组件，也不能宣称稳定支配。`solve_alns_core()` 采用 A2 的默认开关，依据是问题特定引导这一设计目标、三项目标均值与几乎不变的每秒迭代数，而非三种子下的确定性优势。

VND、cluster 和 route pool 在该 240 秒设置下明显降低每秒迭代数，因此不默认开启。ejection 在正式 A4→A5 比较中赢 2 个种子、输 1 个种子，并按任务约束继续保留；本实验没有把 `A2 + ejection` 作为独立正式变体。A5 还启用了 VND 和 cluster repair，A6 又启用了 route pool，所以二者都不能代表 HALNS 的默认开关组合。

## 与前两次实验比较

下面直接沿用三份报告中的方法名称，不再另起名称：第一次报告使用 `C2-Lex-ALNS` 和 `C2-Lex-HALNS`，第二次报告使用 `ALNS Core` 和 `HALNS`，本次使用 A0–A6。

题目规定必须按“逾期任务数 → 总逾期分钟 → 总里程”依次比较，不能把三项加权，也不能因为总里程较短而接受更多逾期任务。六组主要结果如下：

| 实验与方法 | 停止条件 | 种子数 | 平均逾期任务数 | 平均总逾期分钟 | 平均总里程 / km |
|---|---|---:|---:|---:|---:|
| 第一次：C2-Lex-ALNS | 400 轮 | 5 | 83.400 | 3056.266 | 716.337 |
| 第一次：C2-Lex-HALNS | 400 轮 | 5 | 80.600 | 2970.604 | 714.338 |
| 第二次：ALNS Core | 240 秒 | 3 | 70.333 | 2332.834 | 646.561 |
| 第二次：HALNS | 240 秒 | 3 | 70.667 | 2442.069 | 663.445 |
| 本次：A0 | 240 秒 | 3 | 70.333 | 2338.919 | 647.610 |
| 本次：A2 | 240 秒 | 3 | **70.000** | **2321.448** | **643.948** |

第一次只运行 400 轮，实际约 55–70 秒；第二次报告中用于本表的等墙钟结果和本次结果采用 240 秒总预算，并预留 2 秒安全余量。因此第一次数值可以说明固定 400 轮时 `C2-Lex-HALNS` 的三项均值优于 `C2-Lex-ALNS`，但不能与后两次作同时间的算法比较。第二次和本次也属于不同运行批次；跨报告差值只用于查看结果变化，组件效果仍以同一次实验内的比较为准。

### 1. 逾期任务数（late task count）

- 第一次：`C2-Lex-HALNS` 为 `80.600`，比 `C2-Lex-ALNS` 的 `83.400` 少 `2.800`。
- 第二次：`ALNS Core` 为 `70.333`，比 `HALNS` 的 `70.667` 少 `0.333`；逐种子比较为 ALNS Core 赢 2 次、HALNS 赢 1 次。
- 本次：A2 为 `70.000`，比同批 A0 的 `70.333` 少 `0.333`；逐种子比较为 A2 赢 2 次、A0 赢 1 次。

按均值看，A2 的逾期任务数最低。但本次只有三个种子，而且 A0→A1、A1→A2 两个单步比较都各自只有 1 胜 2 负，因此不能断言 assignment destroy 或 deadline risk 单独带来稳定改善。

### 2. 总逾期分钟（total lateness）

只有逾期任务数相同时，总逾期分钟才决定两个方案的先后。

- 第一次：`C2-Lex-HALNS` 比 `C2-Lex-ALNS` 少 `85.662` 分钟。
- 第二次：`ALNS Core` 比 `HALNS` 少 `109.235` 分钟。
- 本次：A2 比同批 A0 少 `17.472` 分钟。

A2 的平均总逾期分钟也是表中最低值。与第二次 `ALNS Core` 相比，A2 的均值少 `11.386` 分钟，但这是两次独立运行的结果差异，不能只归因于本次新增邻域。

### 3. 总里程（distance）

只有逾期任务数和总逾期分钟都相同时，总里程才决定两个方案的先后。

- 第一次：`C2-Lex-HALNS` 比 `C2-Lex-ALNS` 少约 `1.999 km`。
- 第二次：`ALNS Core` 比 `HALNS` 少约 `16.884 km`。
- 本次：A2 比同批 A0 少约 `3.662 km`。

A2 的平均总里程同样是表中最低值。但总里程是第三目标，只有逾期任务数和总逾期分钟都相同时，才用它决定方案优劣。

### 4. 每秒迭代数（iterations/sec）

第二次实验中，`ALNS Core` 平均完成 `1819.3` 轮，`HALNS` 完成 `1036.7` 轮；对应每秒迭代数为 `7.793` 和 `4.441`。更高的每秒迭代数与 `ALNS Core` 在该批次三项均值更低同时出现，可能是原因之一；三个种子不足以证明因果关系。

本次 A2 的每秒迭代数为 `7.094`，A0 为 `7.183`，只下降 `1.25%`。加入 VND 后 A3 降到 `5.385`，再加入 cluster repair 后 A4 降到 `4.633`，A5 和 A6 又分别降到 `4.331` 和 `3.092`。这些更重的配置在本次 240 秒实验中没有换来更少的逾期任务，因此不作为默认设置。

### 5. 240 秒内最好方案（wall-clock best solution）

下表只比较已经保存且通过校验的方案，仍按题目三项目标依次排序。“最好”只指这些已运行的配置和种子，不代表已证明全局最优。

| 来源与方法 | 逾期任务数 | 总逾期分钟 | 总里程 / km | 用时 |
|---|---:|---:|---:|---:|
| [第一次：C2-Lex-HALNS](results/best_fleet_solution_compliant.json) | 76 | 2860.032371 | 694.694821 | 66.36 秒 |
| [第二次：ALNS Core](results/alns_core_comparison/best_alns_core_equal_wall_clock_240s.json) | **67** | **2161.865122** | 631.416943 | 238.02 秒 |
| [本次：A0](results/neighborhood_ablation/run_solutions/equal_wall_clock_240s__a0__seed_2026080502.json) | **67** | 2172.800486 | **631.018272** | 238.00 秒 |

第二次的 `ALNS Core` 与本次 A0 都有 67 个逾期任务；继续比较第二目标，`ALNS Core` 的总逾期少 `10.935` 分钟，因此它是三次正式实验中得分最好的合规方案。本次 A0 虽然总里程少 `0.399 km`，但第三目标不能推翻第二目标的结果。

## 结论、限制与下一步

按题目三项目标，本次 A2 的均值优于同批 A0，而且每秒迭代数只下降 `1.25%`，因此 ALNS Core 默认采用 A2。A3–A6 的平均逾期任务数更高、迭代速度更低，所以 VND、cluster repair 和 route pool 保留为可选功能。第二次报告的 `ALNS Core` 仍给出了三次正式实验中得分最好的合规方案，本次没有刷新该结果。

证据只有一个 200 任务实例。第一次使用 5 个种子但只运行 400 轮；第二次报告中用于本表的等墙钟结果和本次结果均使用 3 个种子及 240 秒总预算。这些种子只反映同一实例上的搜索波动。跨报告结果还会受到运行批次和系统负载影响，所以不能把跨报告差值直接归因于某一个新组件。

下一步应优先完成：

1. 在同一最终源码快照上正式比较 A2 与 `A2 + ejection`，使用相同初始路线、至少 5 个预先固定种子和完整 240 秒预算，补上 HALNS 默认设置的实验结果。
2. 运行脚本已支持但本次未执行的 5 个种子 × 400 轮 A0–A4 消融，区分每轮邻域质量和每秒迭代数。
3. 在多个独立实例上重复配对实验；若继续调优 VND/cluster，应测试降低调用频率、只对高风险任务触发，或在 repair 尚有跨机空槽时运行 relocate。

## 复现与原始数据

完整 A0–A6 墙钟实验命令：

```bash
PYTHONPATH=algorithm/src python3 \
  algorithm/experiments/run_neighborhood_ablation.py \
  --output-dir algorithm/results/neighborhood_ablation \
  --equal-seed-count 0 --wall-seed-count 3 \
  --wall-time-limit 240 --wall-safety-margin 2 \
  --include-hybrid-tuning
```

脚本默认还支持旧实验的 5 个种子 × 400 轮固定迭代消融；本报告的正式数值只来自上面的 240 秒运行。`--resume` 会校验输入、初始路线、参数和实际导入的求解器源码哈希，拒绝混合不同实现的断点结果。结果文件保存了正式运行所用的源码指纹；A0–A6 又都显式指定了各项开关，因此实验结束后的默认值调整不改变本报告记录的算法路径。

原始汇总、逐运行记录、配对比较和 21 份完整路线位于 [`results/neighborhood_ablation/`](results/neighborhood_ablation/)。所有 21 个正式运行均通过独立 validation 且未超预算。
