# ALNS Core 与 HALNS 对比实验报告

## 摘要

本次将求解器明确拆分为两种模式：`C2-Lex-ALNS-Core` 只保留自适应大邻域搜索主循环，`C2-Lex-HALNS` 在同一主循环上增加跨路线驱逐交换和路线池集合划分重组。两者使用完全相同的严格词典序目标：先最小化逾期任务数，再最小化总逾期分钟，最后最小化总里程。

在相同 400 轮、5 个配对随机种子的实验中，ALNS Core 对 HALNS 为 2 胜、0 平、3 负；HALNS 平均逾期数更少，但平均墙钟时间比 Core 高 20.2%。在更符合实际限时求解的相同 240 秒、3 个配对种子实验中，ALNS Core 取得 2 胜、0 平、1 负，平均逾期数为 70.33，略低于 HALNS 的 70.67，并在相同预算下完成了多 75.5% 的搜索迭代。

本次勘误数据重跑得到的最好 ALNS Core 解为 `(67, 2161.865122 min, 631.416943 km)`，正式限时运行用时 238.02 秒，所有 200 项任务的路线均通过独立合法性检查。这一结果支持“当墙钟预算固定时，较轻的 ALNS 主体在当前实例上更有竞争力”，但不构成跨数据集或跨实例的普遍优越性证明。

## 算法定义与实现

ALNS Core 保留 Regret-2 初始解、9 个破坏算子、5 个修复算子、自适应算子权重、模拟退火接受准则、候选位置剪枝和路线评估缓存。新增的 `solve_alns_core()` 公开入口会强制设置 `enable_ejection=False` 与 `enable_route_pool=False`，因此既不运行驱逐交换，也不创建或收集路线池列。

这个定义与历史命令行中的 `basic-alns` 搜索轨迹一致，但修复了两个语义问题：旧实现虽不运行路线池重组，却仍然在持续收集路线列；同时其结果元数据始终标记为 HALNS。新实现使 Core 的路线池列数始终为 0，并正确输出 `C2-Lex-ALNS-Core` 方法名。`basic-alns` 作为兼容别名保留，新命令行名称为 `alns-core`。

为使 HALNS 也能参加墙钟实验，求解器的绝对截止时间被传入驱逐搜索和路线池深度优先搜索，并在破坏、修复和候选评估之间重新检查。单个不可中断的算子仍可能有少量越界，因此实验另外预留 2 秒安全余量，并以实测端到端时间判定是否合规。

## 问题与数据口径

实验使用勘误后的 200 任务数据，生产求解器从同目录 CSV 读取；CSV 的 SHA-256 为 `386d3fbaa9009aeed947493782d657ed0b30b25d369c8187bfc9619fc7e31d25`。问题设置为 8 架无人机，每架最多承担 25 项任务，同时载荷上限为 2，速度为 `0.9 km/min`，起点为数据未提供时的默认值 `(0, 0) km`。路线为开放式，最后一次送达后不计返航里程；取送服务时间为 0，截止时间是软约束。

## 实验设计

对比分为两层。第一层固定为 400 轮，使用种子 `2026080500`–`2026080504`，用于隔离“每轮是否加入强化算子”的影响。Core 重新运行，HALNS 使用同一勘误数据哈希下重新生成的 HALNS 基准记录；5 个 Core 得分全部精确复现历史 `C2-Lex-ALNS` 得分，说明显式 Core 重构没有改变搜索轨迹。固定轮数的墙钟时间只作工程参考，因为两种方法的运行批次不同。

第二层在当前分支上对两种方法都重新运行，使用种子 `2026080500`–`2026080502`，每次总墙钟预算为 240 秒。两者从同一确定性 Regret-2 初始路线开始，初始解时间计入总预算，并预留 2 秒安全余量。种子间交替执行 Core 和 HALNS 的先后顺序，以降低持续系统负载对单一方法的偏置。候选位置上限均为 48，且两者的最大迭代上限都设为 10,000，实际均由墙钟预算停止。

本机记录环境为 macOS 26.5.2、Apple arm64 与 Python 3.14.5。运行顺序、环境、数据哈希和全部原始数值保存在机器可读结果文件中。

## 相同 240 秒墙钟结果

| 方法 | 词典序胜-平-负 | 平均逾期数 | 平均总逾期 / min | 平均距离 / km | 平均迭代数 | 平均迭代数/搜索秒 |
|---|---:|---:|---:|---:|---:|---:|
| ALNS Core | 2-0-1 | 70.33 | 2332.83 | 646.56 | 1819.3 | 7.793 |
| HALNS | 1-0-2 | 70.67 | 2442.07 | 663.44 | 1036.7 | 4.441 |

ALNS Core 的平均逾期数比 HALNS 少 0.33（相对 HALNS 为 0.47%），平均总逾期低 109.23 分钟（4.47%），平均距离低 16.88 km（2.54%）。平均总用时分别为 238.06 秒和 238.05 秒，实际墙钟预算相当。Core 每秒迭代数高 75.5%，平均多搜索 782.7 轮。Core 平均逾期数的 95% Student-t 描述性区间半宽为 7.17，HALNS 为 5.17，这一宽区间也直接显示 3 个种子不足以支持稳定性宣称。

配对差的中位数与均值还呈现不同方向：Core 减 HALNS 的总逾期中位差为 `+4.97 min`，距离中位差为 `-12.55 km`。总逾期的平均改善主要由种子 `2026080502` 的较大优势驱动；距离则在 3 个种子中均由 Core 更短，因此不应写成“每项指标每次都稳定更好”。

| 随机种子 | ALNS Core 得分 | Core 迭代 | HALNS 得分 | HALNS 迭代 | 胜者 |
|---:|---:|---:|---:|---:|---|
| 2026080500 | `(72, 2447.38, 654.57)` | 1804 | `(69, 2442.41, 667.12)` | 1059 | HALNS |
| 2026080501 | `(72, 2389.25, 653.70)` | 1878 | `(73, 2363.12, 656.31)` | 1000 | ALNS Core |
| 2026080502 | `(67, 2161.87, 631.42)` | 1776 | `(70, 2520.68, 666.91)` | 1051 | ALNS Core |

因为目标是严格词典序，种子 `2026080501` 中 Core 以少 1 项逾期获胜，即使 HALNS 的总逾期更低，也不会颠倒第一目标的优先级。

## 与上一次结果的关系

本次勘误数据的 400 轮 HALNS 最好解为 `(76, 2860.032371, 694.694821)`。本次等墙钟 ALNS Core 最好解为 `(67, 2161.865122, 631.416943)`，少 9 项逾期，总逾期低 24.41%，距离低 9.11%。不过，400 轮 HALNS 在约 66 秒就停止，因此这项对照只能说明“本次在更充分地使用 240 秒预算后找到了更好解”，不是公平的算法速度对比。

同一勘误数据的 1500 轮离线扩展 HALNS 得到 `(67, 2272.192060, 641.635947)`，用时 338.81 秒。本次 Core 与它的逾期数相同，在词典序的第二层将总逾期再降低 110.33 分钟（4.86%），距离降低 10.22 km（1.59%），且正式运行仍在 240 秒内。

## 结论与限制

固定迭代实验表明，HALNS 的单轮搜索质量在当前实例上平均更好；等墙钟实验则表明，驱逐交换和路线池重组的成本使 HALNS 吞吐量明显下降，Core 通过更多的主循环迭代在 3 个种子中赢下 2 个。因此，在当前实例与参数下，若场景具有硬性墙钟预算，可将 ALNS Core 作为优先候选，但跨实例的方法选择仍需额外验证；如果以固定迭代数研究每轮算子强度，HALNS 仍展示出正向平均效果。

本报告的证据局限很明确：只有一个 200 任务实例，固定迭代实验为 5 个种子，而成本更高的等墙钟实验只有 3 个种子。随机种子只描述同一实例上的搜索波动，不是独立问题实例。因此本次不报告 p 值，均值与 95% Student-t 区间只作描述性统计，不将它们解释为跨数据集的总体保证。墙钟时间还受硬件和系统负载影响；起点、服务时间和开放路线是当前数据缺失下的建模假设；候选位置剪枝也可能排除部分优质移动。后续应在多个独立实例上增加预先固定的配对种子，并分别对驱逐交换和路线池重组做单独消融。

## 验证与复现

本次新增了 Core 强制关闭强化模块、方法元数据、CLI 输出、严格词典序配对比较与断点续跑测试。完整测试集为 34 项，全部通过。正式实验的 16 条记录均标记为合法，6 条等墙钟记录均低于 240 秒。

从仓库根目录执行：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt -e .
PYTHONPATH=algorithm/src .venv/bin/python -m pytest algorithm/tests -q
```

```bash
PYTHONPATH=algorithm/src .venv/bin/python \
  algorithm/experiments/run_alns_core_comparison.py \
  --output-dir algorithm/results/alns_core_comparison \
  --equal-seed-count 5 --equal-iterations 400 \
  --wall-seed-count 3 --wall-time-limit 240 \
  --wall-safety-margin 2
```

实验脚本每完成一次运行就写入断点文件，中断后可在同一命令末尾增加 `--resume`。主要产物如下：

- `algorithm/results/alns_core_comparison/comparison_results.json`：环境、参数、全部原始运行、汇总和配对胜负。
- `algorithm/results/alns_core_comparison/comparison_runs.csv`：每个种子的可审计记录。
- `algorithm/results/alns_core_comparison/comparison_summary.csv`：均值、中位数、样本标准差与 95% 区间半宽。
- `algorithm/results/alns_core_comparison/best_alns_core_equal_iterations_400.json`：固定 400 轮实验中最好 Core 完整路线。
- `algorithm/results/alns_core_comparison/best_alns_core_equal_wall_clock_240s.json`：正式等墙钟记录中 1776 轮 Core 运行的最好完整路线；得分与正式记录一致。
- `algorithm/results/alns_core_comparison/best_halns_equal_wall_clock_240s.json`：本次等墙钟 HALNS 的最好完整路线。
- `algorithm/results/alns_core_comparison/run_solutions/`：每次正式运行写出的完整路线文件，供逐条审计。
- `algorithm/results/alns_core_comparison/validation_report.json`：两份最佳路线的独立复算得分、合法性结论与文件哈希。
